**Found 2026-07-18**: `sensor.gplugk_z_ei` (grid-import meter) went silent at 2026-07-18 06:28 CEST because solar covered 100% of household load — confirmed via the HA history API that the sensor pushes no periodic update when its cumulative value doesn't change, it simply stops emitting states. **Fixed same day**, branch `fix/trailing-sensor-silence-lag-gap` off `dev`, commits `d064797` (Task 1: `end_time` param on `_raw_to_kwh_diff()`), `9c6cae8`+`9964847` (Task 2: `fetch_recent_energy()`, plus a collateral tz/assertion fix on a pre-existing test), `a2bcd83`+`7292166` (Task 3: `fetch_energy_history()`, plus a collateral fix on 3 pre-existing tests), `b45e4d5` (Task 4: `fetch_energy_history_15m()`), `1ef2fe5` (Task 5: `fetch_recent_energy_15m()`).

**Root cause — distinct from [[project_zero_diff_cache_gap_fix]]:** that earlier fix (2026-07-17) handled the case where the sensor *still emits a state each poll* but the diff between consecutive states is exactly `0.0` — the old `>0` filter dropped those interior rows even though `ffill()` had already produced them. This fix handles a different failure mode: the sensor stops emitting *any* state at all. `pandas.Series.resample(resolution).last()` only generates bins up to the last timestamp actually present in the raw input — it never extends forward to "now." So when the source sensor goes fully silent, every hour after its last real push is simply *absent* from the resampled series (no row to even apply `ffill()`/the `>=0` filter to), not merely filtered out. The 2026-07-17 fix could not have caught this — it only widened a filter on rows that already existed.

**Fix:** added an opt-in `end_time: pd.Timestamp | None = None` param to `_raw_to_kwh_diff()` (the single shared helper used by all four fetch paths, per the `#85` 15m-cache extraction). When given, the resampled series is `reindex()`ed through `end_time` *before* `ffill()` — extending the same "flat gap ⇒ 0.0 diff" semantics `ffill()` already applies to interior gaps, to the open-ended trailing gap relative to "now." Wired `end_time=pd.Timestamp.now(tz=timezone)` into all 4 call sites: `fetch_recent_energy()`, `fetch_energy_history()`, `fetch_energy_history_15m()`, `fetch_recent_energy_15m()`. Default `None` preserves old behavior exactly for any unmigrated caller.

**Collateral test fixes were necessary, not scope creep:** wiring a real `end_time=now()` into a call site exposed two latent problems in *pre-existing, unrelated* tests whose HA-raw fixtures used unrealistic old fixed dates (e.g. `2024-01-01`) — because the reindex now spans from that old date through "now" (~2.5 years, tens of thousands of trailing zero-kWh rows):
1. Fixtures built with **naive (non-tz-aware) timestamps** crashed with `TypeError: Cannot compare tz-naive and tz-aware timestamps` (real `_fetch_history()` output is always tz-aware, so the naive fixture was already unrealistic, just latent).
2. Fixtures asserting **exact row counts** (`len(result) == N`) became vacuous once thousands of legitimate trailing zero-rows appeared — the assertion still "passed" but no longer verified what its docstring claimed.
Both were caught by task review, not by the initial implementer or by the test suite going red — the suite stayed green with a weakened assertion in the first draft. Fixed by switching naive fixtures to the file's `make_ha_raw()` tz-aware idiom, and tightening count-based assertions to check a specific value at a specific timestamp instead.
