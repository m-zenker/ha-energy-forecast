**Post-deploy hotfix (2026-07-10, commit `058b963` on dev):** `_publish_physics_sensors()` crashed every hourly cycle with `AttributeError: 'EnergyForecast' object has no attribute '_physics_climate_dfs'` the first time `physics:` was live-enabled — only `_physics_heating_buffer_df` had been defensively initialized in `initialize()` (an existing comment literally said to guard against exactly this "fires before first retrain" scenario, but wasn't applied to the other four sibling attributes: `_physics_climate_dfs`, `_physics_dhw_tank_df`, `_physics_cop_df`, `_room_thermostat_temp_dfs`). Existing tests in `TestPhysicsSensors` didn't catch this because they use a bare `MagicMock()` for `self`, which auto-vivifies missing attributes instead of raising `AttributeError` like a real object — wrote a new regression test (`test_physics_history_attrs_defensively_initialized_before_first_retrain`) that discriminates via explicit value assertions (`== {}`/`is None`, which a MagicMock auto-vivified attribute would fail), verified RED before the fix and GREEN after, then redeployed. Confirmed live: `sensor.ha_energy_forecast_energy_forecast_physics_base_today`/`_ml_adjustment_today` now publish real values.

**First live physics calibration results (2026-07-10, mid-summer):** `Q_base_el=0.133`, `Q_dhw_daily=3.80`, `UA_dhw=3.11` all calibrated successfully from real data (DHW draw/decay patterns have enough summer signal). `UA_eff` (space-heating envelope) calibration failed and was discarded (R²=0.09 — no real heating cycles to observe in July) and stays at its config default; `solar_gain_area` is consequently 0. So `physics_base_today` right now is essentially "base load + DHW simulation," with the space-heating physics component contributing ~nothing until winter data lets `UA_eff` calibrate — this is the expected, designed behavior of the cold-start gate, not a bug.
